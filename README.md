# shortlink

REST API сервиса сокращения ссылок на Go, с аналитикой переходов, JWT-аутентификацией и rate limiting. Небольшой проект, где на знакомой предметной области разобраны архитектурные и конкурентные паттерны: слоистая структура, асинхронная запись через буферизующий воркер, graceful shutdown, тесты на in-memory fakes вместо моков.

## Стек

| Компонент         | Технология                              | Почему                                                                                                                                                   |
| ------------------ | ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Язык                | Go                                       | —                                                                                                                                                         |
| HTTP                | `net/http`, роутер из стандартной библиотеки | Go 1.22+ умеет матчинг по методу и wildcard-параметры; middleware пишется вручную — демонстрирует понимание stdlib, а не умение подключить фреймворк         |
| База данных         | PostgreSQL, драйвер `pgx`                | Нативный клиент Postgres: контроль над пулом соединений, простой разбор SQLSTATE через `*pgconn.PgError`. `database/sql` даёт абстракцию над СУБД, которая в однобазовом проекте ничего не даёт |
| Кэш                 | in-memory, для «горячих» ссылок          | Демонстрирует принцип — кэш перед БД для горячего пути — без лишней инфраструктуры. Интерфейс `Cacher` спроектирован так, что Redis-реализация подключается позже без изменений в вызывающем коде |
| Аутентификация      | JWT + bcrypt                             | Отработанный паттерн, без внешних зависимостей                                                                                                           |
| Контейнеризация     | Docker, docker compose                   | Одна команда для запуска, миграции применяются автоматически                                                                                             |

## Архитектура

```
HTTP-запрос
    │
    ▼
handler   — разбор запроса, статус-коды, JSON
    │
    ▼
service   — бизнес-правила: генерация кода, владение ссылкой,
    │        user enumeration guard, rate limiting
    ▼
repository — доступ к PostgreSQL через интерфейсы
    │
    ▼
PostgreSQL
```

Клики по ссылкам не пишутся в БД синхронно — `ClickWorker` копит их в
канале и сбрасывает пачками по таймеру или по размеру батча, чтобы
редирект не ждал вставки в базу. `Scheduler` отдельным тикером удаляет
просроченные ссылки в фоне.

```
cmd/api/            — точка входа, сборка зависимостей, миграции, graceful shutdown
internal/
  handler/           — HTTP-хендлеры
  service/           — бизнес-логика
  repository/         — доступ к БД (Postgres-реализации + интерфейсы)
  model/              — DTO и доменные структуры
  middleware/          — аутентификация, rate limiting
  worker/              — ClickWorker, Scheduler
  cache/               — in-memory кэш ссылок
  apperrors/           — sentinel-ошибки и их маппинг в HTTP-статусы
pkg/
  auth/                — JWT, хеширование паролей
  database/            — пул соединений с PostgreSQL
migrations/            — SQL-миграции
```

Критерий `internal/` vs `pkg/`: в `pkg/` — то, что не завязано на
домен сервиса и потенциально можно переиспользовать в другом проекте
(JWT, хеширование, работа с пулом соединений). Всё, что знает про
ссылки, пользователей и клики, живёт в `internal/`.

## Graceful shutdown

При `SIGTERM`/`SIGINT` сервис останавливается в фиксированном порядке:
HTTP-сервер → воркер кликов → планировщик очистки. Порядок не
произвольный.

HTTP-сервер останавливается первым: перестаёт принимать новые запросы,
но дожидается завершения уже идущих. Если остановить воркер до
HTTP, ещё идущий редирект может вызвать `Record` на уже закрытом
канале и упасть. К моменту остановки воркера новых кликов уже нет, и
`Stop()` сливает финальный буфер в БД, а не гонится за растущим
потоком. Планировщик останавливается последним: ему не критично
закончить текущий проход очистки — недочищенные ссылки удалятся на
следующем тике после перезапуска.

`Shutdown` на HTTP-сервере ограничен 10-секундным таймаутом, чтобы
клиент, держащий соединение, не мог заблокировать остановку навсегда.

## Решения по схеме

- **`BIGSERIAL`, а не `UUID`.** `clicks` — самая быстрая по росту
  таблица в проекте. Случайные UUID-ключи фрагментируют B-tree индекс
  при вставке; монотонный `BIGSERIAL` всегда вставляется в «правый
  край» индекса.
- **`UNIQUE` как единственный источник истины для дубликатов.**
  Наивный подход «проверить, затем вставить» содержит гонку.
  Правильно — пытаться вставить и ловить ошибку Postgres `23505`,
  транслируя её в `ErrDuplicateUser` / `ErrDuplicateShortCode`.
- **Частичный индекс на `expires_at`.** Воркер очистки выбирает
  только просроченные строки; `NULL` (бессрочные ссылки) в выборку
  никогда не попадают — индексировать их бессмысленно.
- **`TIMESTAMPTZ`, а не `TIMESTAMP`.** Хранит момент времени
  однозначно (внутри — UTC), корректно конвертирует при чтении.
- **`original_url` типа `TEXT`.** URL с UTM-метками и токенами бывают
  очень длинными; жёсткий лимит рано или поздно обрежет валидную
  ссылку.

## Быстрый старт

Оба варианта работают сразу после `git clone`, без дополнительной
настройки — нужен только запущенный PostgreSQL.

### Локально

```bash
export DATABASE_URL="postgres://shortlink:shortlink@localhost:5432/shortlink?sslmode=disable"
export JWT_SECRET="dev-secret"
go run ./cmd/api
```

### Через Docker

```bash
docker compose up --build
```

Поднимает сервис вместе с PostgreSQL, применяет миграции автоматически
при старте. Приложение слушает `:8080` на хосте.

## API

| Метод и путь                    | Аутентификация | Описание                              |
| -------------------------------- | --------------- | -------------------------------------- |
| `POST /api/register`              | нет              | регистрация пользователя               |
| `POST /api/login`                 | нет              | вход, выдает JWT                       |
| `POST /api/links`                 | да               | создать короткую ссылку (rate limited) |
| `DELETE /api/links/{id}`          | да               | удалить свою ссылку                    |
| `GET /api/links/{id}/stats`        | да               | статистика переходов по своей ссылке   |
| `GET /{shortCode}`                | нет              | редирект на оригинальный URL           |
| `GET /api/health`                 | нет              | health-check                           |

Ниже — рабочие примеры на `localhost:8080`. Токен из ответа `/api/login`
удобно сразу положить в переменную через `jq` (если он установлен) —
иначе просто скопируйте значение `token` из ответа вручную.

```bash
# Регистрация
curl -s -X POST http://localhost:8080/api/register \
  -H 'Content-Type: application/json' \
  -d '{"username":"alice","email":"alice@example.com","password":"secret123"}'

# Вход
curl -s -X POST http://localhost:8080/api/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"alice@example.com","password":"secret123"}'

# Сохранить токен (нужен jq)
TOKEN=$(curl -s -X POST http://localhost:8080/api/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"alice@example.com","password":"secret123"}' | jq -r .token)

# Создать короткую ссылку
curl -s -X POST http://localhost:8080/api/links \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"original_url":"https://example.com"}'

# Редирект (short_code — из ответа выше)
curl -i http://localhost:8080/<short_code>

# Статистика по ссылке (id — из ответа на создание)
curl -s http://localhost:8080/api/links/<id>/stats \
  -H "Authorization: Bearer $TOKEN"

# Удалить ссылку
curl -s -X DELETE http://localhost:8080/api/links/<id> \
  -H "Authorization: Bearer $TOKEN"

# Health-check
curl -i http://localhost:8080/api/health
```

## Переменные окружения

| Переменная                  | Обязательна | По умолчанию | Назначение                                     |
| ---------------------------- | ------------ | ------------ | ------------------------------------------------ |
| `DATABASE_URL`                | да           | —            | DSN подключения к PostgreSQL                     |
| `JWT_SECRET`                  | да           | —            | секрет для подписи JWT                           |
| `PORT`                        | нет          | `8080`       | порт, на котором слушает HTTP-сервер             |
| `APPLY_MIGRATIONS_ON_START`   | нет          | `true`       | применять ли миграции автоматически при старте   |

## Что можно улучшить

- Общие in-memory fakes для тестов продублированы в пакетах `service`
  и `handler` — стоило бы вынести их в `internal/testutil`.
- Нет бенчмарков для in-memory кэша.
- Нет CI (GitHub Actions) — тесты и `go vet` пока запускаются только
  локально.
- Health-check не проверяет доступность БД, только то, что процесс
  жив.
- Rate limiter — fixed window и только в памяти процесса: при
  нескольких инстансах сервиса лимит не общий.
