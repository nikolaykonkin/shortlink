# shortlink

[![CI](https://github.com/nikolaykonkin/shortlink/actions/workflows/ci.yml/badge.svg)](https://github.com/nikolaykonkin/shortlink/actions/workflows/ci.yml)

REST API сервиса сокращения ссылок на Go, с аналитикой переходов, JWT-аутентификацией и rate limiting (in-memory и Redis). Небольшой проект, где на знакомой предметной области разобраны архитектурные и конкурентные паттерны: слоистая структура, асинхронная запись через буферизующий воркер, graceful shutdown, тесты на in-memory fakes вместо моков.

| --------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------ |

## Архитектура

```
HTTP-запрос
    │
    ▼
handler   — разбор запроса, статус-коды, JSON
    │
    ▼
service   — бизнес-правила: генерация кода, владение ссылкой,
    │        user enumeration guard
    ▼
repository — доступ к PostgreSQL через интерфейсы
    │
    ▼
PostgreSQL
```

Rate limiting и аутентификация живут в `middleware` — это HTTP-слой, который не знает о домене.

Клики по ссылкам не пишутся в БД синхронно: `ClickWorker` копит их в канале и сбрасывает пачками по таймеру или по размеру батча, чтобы редирект не ждал вставки. `Scheduler` отдельным тикером удаляет просроченные ссылки в фоне.

```
cmd/api/            — точка входа, сборка зависимостей, миграции, graceful shutdown
internal/
  apperrors/         — sentinel-ошибки и их маппинг в HTTP-статусы
  cache/             — in-memory кэш ссылок (Cacher + MemoryCache)
  handler/           — HTTP-хендлеры
  middleware/        — аутентификация, rate limiting (RateStore + две реализации)
  model/             — DTO и доменные структуры
  repository/        — доступ к БД (интерфейсы + Postgres-реализации)
  service/           — бизнес-логика
  worker/            — ClickWorker, Scheduler
pkg/
  auth/              — JWT, хеширование паролей
  database/          — пул соединений с PostgreSQL
migrations/          — SQL-миграции
```

Критерий `internal/` vs `pkg/`: в `pkg/` — то, что не завязано на домен сервиса и потенциально переиспользуется в другом проекте (JWT, хеширование, работа с пулом). Код, который знает про ссылки, пользователей и клики, живет в `internal/`. `pkg/` не зависит от `internal/`: ошибки JWT объявлены в `pkg/auth`, а не в `internal/apperrors`.

## Технические решения

### Слоистая архитектура

Зависимости направлены внутрь: `handler` → `service` → `repository`. Сервисный слой зависит от **интерфейсов** репозиториев, а не от `pgxpool.Pool` напрямую. Это дает две вещи: тестируемость без БД (в тестах — in-memory fakes) и возможность заменить хранилище без переписывания бизнес-логики.

### Асинхронный подсчет кликов

Редирект не должен ждать вставки клика в БД.

<details>
<summary>Почему канал, а не синхронная запись</summary>

Клик — метрика, а не транзакция. Синхронная запись добавила бы миллисекунды к каждому редиректу на горячем пути, где все конкурируют за одни и те же соединения пула. Канал разрывает эту связь: хендлер отдает ответ сразу, воркер пишет батчами по размеру или по тикеру.

</details>

<details>
<summary>Почему отправка в канал неблокирующая</summary>

```go
select {
case w.queue <- linkID:
default:
    log.Printf("канал кликов переполнен, клик потерян")
}
```

При переполнении канала клик отбрасывается, а не блокирует горутину-обработчик HTTP-запроса. Осознанный компромисс: потерять одну запись статистики дешевле, чем задержать редирект — наивный `w.queue <- linkID` выглядит безобидно, но при медленном воркере заблокирует весь HTTP-сервер.

</details>

<details>
<summary>Почему CopyFrom, а не INSERT ... VALUES</summary>

```go
r.pool.CopyFrom(ctx, pgx.Identifier{"clicks"}, []string{"link_id"}, pgx.CopyFromRows(rows))
```

`COPY` — самый быстрый способ массовой вставки в Postgres: одна команда, один сетевой обмен, без построения большого SQL-запроса с параметрами. Для батча в 50 кликов разница с `INSERT ... VALUES (...), (...) ...` заметна уже на сотнях записей в секунду. `RETURNING` не используется — воркеру нужны только идентификаторы строк, а не сами строки.

</details>

### Кэш горячих ссылок

Перед обращением к БД на редиректе — проверка кэша по `short_code`. Реализация — `map[string]*model.Link` под `sync.RWMutex`.

<details>
<summary>Почему RWMutex, а не sync.Map</summary>

`sync.Map` оптимизирован под сценарий, где ключи почти не пересекаются между горутинами (или один ключ пишется одной горутиной, а читается многими). Для кэша ссылок характерна другая картина: **частые чтения и редкие записи по одним и тем же ключам**. В этом сценарии `RWMutex` с обычной `map` дает лучшую производительность, потому что позволяет множеству читателей работать параллельно без накладных расходов внутренней организации `sync.Map`.

</details>

<details>
<summary>Инвалидация при удалении</summary>

`LinkService.Delete` вызывает `s.cache.Delete(link.ShortCode)` после успешного удаления из БД. Без этого удаленная ссылка продолжала бы отдаваться из кэша до перезапуска сервиса. В проекте на один инстанс этого достаточно; в распределенной системе понадобился бы pub/sub или TTL — это явно отложено в «Что можно улучшить».

</details>

<details>
<summary>Проверка expires_at при попадании в кэш</summary>

```go
if link, ok := s.cache.Get(shortCode); ok {
    if isExpired(link) {
        return nil, apperrors.ErrLinkNotFound
    }
    return link, nil
}
```

Запись в кэше не узнает о наступлении своего `expires_at` сама. Если проверять срок только при чтении из БД, просроченная ссылка могла бы отдаваться из кэша до перезапуска. Поэтому `isExpired` вызывается в обеих ветках.

</details>

### Rate limiting

Fixed-window счетчик с двумя реализациями за интерфейсом `RateStore`.

<details>
<summary>Зачем интерфейс RateStore</summary>

Изначально счетчики жили прямо в `RateLimiter` (`map[int64]int` под мьютексом). Это работает, пока инстанс один. С несколькими инстансами каждый считает свой лимит, и пользователь получает `N × limit`. Интерфейс отделяет «как ограничиваем» (HTTP-слой) от «где лежат счетчики»:

```go
type RateStore interface {
    Allow(ctx context.Context, key string, limit int, window time.Duration) (bool, error)
}
```

Две реализации: `MemoryRateStore` (по умолчанию, для локальной разработки) и `RedisRateStore` (счетчик `INCR` + `PEXPIRE` в одном Lua-скрипте). Выбор — через `RATE_STORE=memory|redis`.

</details>

<details>
<summary>Почему Lua-скрипт в Redis, а не отдельные INCR и PEXPIRE</summary>

Между `INCR` и `PEXPIRE`, отправленными двумя командами, соединение может оборваться. Ключ останется без TTL — счетчик будет расти вечно, и пользователь окажется заблокирован навсегда. Redis выполняет Lua-скрипт целиком, не вклинивая команды других клиентов.

```lua
local current = redis.call('INCR', KEYS[1])
if current == 1 then
    redis.call('PEXPIRE', KEYS[1], ARGV[1])
end
if current > tonumber(ARGV[2]) then
    return 0
end
return 1
```

`PEXPIRE` (миллисекунды), а не `EXPIRE` (секунды): окно короче секунды при округлении до секунд стало бы нулем, и Redis сразу удалил бы ключ — лимит перестал бы работать.

</details>

<details>
<summary>Почему fail-closed, а не откат на memory</summary>

Если Redis настроен, но недоступен, `Allow` возвращает ошибку, и middleware отвечает `503`. Автоматический откат на in-memory счетчик молча превратил бы общий лимит в `N × limit` именно в тот момент, когда система нездорова. Лучше явный отказ, чем несогласованное поведение. По той же причине недоступный Redis при старте — `log.Fatal`, а не тихий переход в другой режим.

</details>

<details>
<summary>Различие окон в memory и redis</summary>

`MemoryRateStore` использует одно общее окно на все ключи, сбрасывается целиком. `RedisRateStore` ставит TTL на каждый ключ отдельно — окно пользователя начинается с его первого запроса. Для лимита «10 в минуту» разница несущественна: memory проще, redis точнее по границам окна.

</details>

### Защита от user enumeration

`UserService.Login` возвращает **одну и ту же** `ErrInvalidCredentials` в двух сценариях: email не найден и email найден, но пароль не подошел. Если бы API отвечал по-разному, по разнице ответов можно было бы определить, какие email зарегистрированы в системе. Тест на это использует `errors.Is`, а не сравнение текста — текст совпадает, важна идентичность ошибки.

### Генерация коротких кодов

Случайная строка base62 длиной 7 символов + повторная генерация при коллизии до `maxAttempts` (5). Предохранитель отличает «не повезло» от «пространство кодов исчерпано»: при исчерпании возвращается `ErrShortCodeSpaceExhausted`, который маппится в `503`. Отклоненные альтернативы: base62 от auto-increment ID (последовательные и предсказуемые коды) и хеш от URL (дедупликация часто нежелательна — пользователи хотят разные ссылки на один URL для раздельной аналитики).

## Graceful shutdown

При `SIGTERM`/`SIGINT` сервис останавливается в фиксированном порядке — от HTTP-слоя к инфраструктуре, потому что каждый следующий компонент зависит от того, что предыдущий уже закончил.

```
HTTP-сервер  →  clickWorker  →  scheduler  →  redis client  →  pool
```

<details>
<summary>Что сломается при другом порядке</summary>

1. **HTTP первым.** Перестает принимать новые запросы, но дожидается завершения идущих. Если остановить воркер до HTTP, еще идущий редирект может вызвать `Record` на закрытом канале — паника.
2. **Worker вторым.** К этому моменту новых кликов уже нет, и `Stop()` сливает финальный буфер, а не гонится за растущим потоком.
3. **Scheduler третьим.** Ему не критично закончить текущий проход очистки — недочищенные ссылки удалятся на следующем тике после перезапуска.
4. **Redis client четвертым.** Rate limiter ходит в Redis из обработчиков — клиент должен жить, пока HTTP-сервер еще не остановлен.
5. **Pool последним.** Оба воркера уже закончили свои последние обращения к БД.

`Shutdown` HTTP-сервера ограничен 10-секундным таймаутом: зависший клиент не должен блокировать остановку контейнера.

</details>

## Решения по схеме

- **`BIGSERIAL`, а не `UUID`.** `clicks` — самая быстрорастущая таблица. Случайные UUID фрагментируют B-tree индекс при вставке; монотонный `BIGSERIAL` всегда вставляется в правый край индекса. Наружу отдается `short_code`, а не ID.
- **`UNIQUE` как единственный источник истины для дубликатов.** Наивный подход «проверить, затем вставить» содержит гонку. Правильно — пытаться вставить и ловить ошибку Postgres `23505`, транслируя ее в `ErrDuplicateUser` / `ErrDuplicateShortCode`.
- **Частичный индекс на `expires_at`.** Воркер очистки выбирает только просроченные строки; `NULL` (бессрочные ссылки) в выборку не попадают никогда — индексировать их бессмысленно.
- **`TIMESTAMPTZ`, а не `TIMESTAMP`.** Хранит момент времени однозначно (внутри — UTC), корректно конвертирует при чтении.
- **`original_url` типа `TEXT`.** URL с UTM-метками и токенами бывают очень длинными; жесткий `VARCHAR(255)` рано или поздно обрежет валидную ссылку.
- **Каскадное удаление по обеим связям.** Клик без ссылки нечитаем; ссылка без владельца противоречит модели.

### Миграции

Для локальной разработки — минимальный раннер: применяет `*.up.sql` из `migrations/` и отмечает примененные в `schema_migrations`, оборачивая выполнение файла и запись в таблицу в одну транзакцию — иначе падение на середине файла оставило бы схему и учет в рассогласованном состоянии. Для production — `golang-migrate` CLI: файлы уже названы по его конвенции, переименовывать ничего не надо.

Автоприменение при старте отключается переменной `APPLY_MIGRATIONS_ON_START=false`. Раннер сознательно минимальный — нет защиты от гонки между одновременно стартующими инстансами, — но для одного локального инстанса этого достаточно.

## Быстрый старт

### Локально

Нужен запущенный PostgreSQL. Поднять только его в Docker:

```bash
docker compose up -d postgres
```

Затем запустить приложение:

```bash
export DATABASE_URL="postgres://shortlink:shortlink@localhost:5432/shortlink?sslmode=disable"
export JWT_SECRET="dev-secret"
go run ./cmd/api
```

### Через Docker

PostgreSQL и Redis поднимаются автоматически вместе с сервисом, `RATE_STORE=redis` включается через переменные окружения в `docker-compose.yml`, миграции применяются при старте:

```bash
docker compose up --build
```

Приложение слушает `:8080` на хосте.

### Режим rate limiter

По умолчанию — in-memory счетчики (для одного инстанса). Для распределенного режима:

```bash
RATE_STORE=redis REDIS_ADDR=localhost:6379 go run ./cmd/api
```

## API

| Метод и путь                | Аутентификация | Описание                                                                                                    |
| --------------------------- | -------------- | ----------------------------------------------------------------------------------------------------------- |
| `POST /api/register`        | нет            | регистрация пользователя                                                                                    |
| `POST /api/login`           | нет            | вход, выдает JWT                                                                                            |
| `POST /api/links`           | да             | создать короткую ссылку (rate limited)                                                                      |
| `DELETE /api/links/{id}`    | да             | удалить свою ссылку                                                                                         |
| `GET /api/links/{id}/stats` | да             | статистика переходов по своей ссылке                                                                        |
| `GET /{shortCode}`          | нет            | редирект на оригинальный URL                                                                                |
| `GET /api/health`           | нет            | health-check (проверяет ping только PostgreSQL; недоступность Redis видна как 503 на rate-limited запросах) |

Примеры на `localhost:8080`. Токен удобно сразу положить в переменную через `jq`, если он установлен, — иначе скопируйте значение из ответа вручную.

```bash
# Регистрация
curl -s -X POST http://localhost:8080/api/register \
  -H 'Content-Type: application/json' \
  -d '{"username":"alice","email":"alice@example.com","password":"secret123"}'

# Вход + сохранение токена
TOKEN=$(curl -s -X POST http://localhost:8080/api/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"alice@example.com","password":"secret123"}' | jq -r .token)

# Создать короткую ссылку
curl -s -X POST http://localhost:8080/api/links \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"original_url":"https://example.com"}'

# Редирект (short_code — из ответа выше)
curl -i http://localhost:8080/<short_code>

# Статистика по ссылке (id — из ответа на создание)
curl -s http://localhost:8080/api/links/<id>/stats \
  -H "Authorization: Bearer $TOKEN"

# Удалить ссылку
curl -s -X DELETE http://localhost:8080/api/links/<id> \
  -H "Authorization: Bearer $TOKEN"

# Health-check
curl -i http://localhost:8080/api/health
```

## Тесты

```bash
go test ./...
go test -race ./...
```

Покрыто: сервисный слой, `ClickWorker`, `Scheduler`, `MemoryRateStore` и `RedisRateStore` (через `miniredis`), `RateLimiter` с обеими реализациями, HTTP-хендлеры через реальный `AuthMiddleware` с настоящим JWT, health-check с fake `Pinger`. Тесты используют in-memory fakes, а не mock-библиотеки. Redis-режим дополнительно проверялся вручную против настоящего Redis в Docker.

## Производительность

```bash
go test -bench=. -benchmem ./internal/cache/
```

На Apple M1:

```
BenchmarkMemoryCache_Get_Hit-8      15533257    82.22 ns/op    0 B/op    0 allocs/op
BenchmarkMemoryCache_Get_Miss-8     86788810    13.83 ns/op    0 B/op    0 allocs/op
BenchmarkMemoryCache_Set-8          56827152    20.86 ns/op    0 B/op    0 allocs/op
```

Все три сценария — 0 аллокаций. `Get_Hit` запускается через `b.RunParallel`, `Get_Miss` — последовательным циклом: это разные режимы нагрузки, и числа из них напрямую сравнивать нельзя. Разница показывает не «hit медленнее miss», а издержки синхронизации за `RWMutex.RLock` под параллельной нагрузкой — это и есть реальный паттерн редиректов, где много горутин одновременно читают один и тот же ключ.

## Что можно улучшить

- **`internal/testutil` для общих fakes.** Fake-репозитории дублируются между `service`, `handler` и `worker` тестами. В production-проекте их вынесли бы в отдельный пакет, но здесь дублирование дешевле, чем пакет, знающий про все интерфейсы репозиториев сразу.
- **Sliding-window для rate limiter.** Сейчас fixed-window (счетчик со сбросом окна целиком): пользователь может выполнить почти двойной лимит на границе двух окон. Sliding-window (окно скользит по времени, а не сбрасывается целиком) устранил бы этот эффект, но требует более сложной структуры данных.
- **Вытеснение записей из `MemoryCache`.** Кэш не ограничен по размеру и не вытесняет старые записи. LRU или TTL решили бы это, но добавляют сложность, не обязательную для демонстрации механизма.
- **Redis для кэша ссылок.** Интерфейс `Cacher` уже спроектирован так, что Redis-реализация подключается без изменений в вызывающем коде — но это расширение не входит в текущий объем.
- **Health-check только для PostgreSQL.** Если `RATE_STORE=redis` и Redis недоступен, `/api/health` продолжает отвечать 200, а rate-limited запросы — 503. Стоит добавить проверку Redis в health-check, чтобы балансировщик видел отказ на обоих хранилищах.
